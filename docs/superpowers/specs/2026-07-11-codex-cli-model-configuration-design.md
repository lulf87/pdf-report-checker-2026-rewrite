# Codex CLI Model Configuration Design

## Goal

Allow operators to configure the default Codex CLI model and allow users to override that model per PTR compare or report-check task without changing global runner state.

## Scope

- Add a server default model setting.
- Add a server-configured list of model options for the frontend.
- Add an optional task-level model override to PTR compare and report-check uploads.
- Add a model selector with a custom model input to both upload forms.
- Include the effective model in runtime metadata and Codex review cache isolation.
- Preserve the current behavior when no model is configured.

The feature does not change report-check C01-C11 or PTR comparison rules.

## Configuration

`Settings` gains two additive fields:

- `CODEX_AUDIT_MODEL`: optional default model identifier. When empty, the runner omits `--model` and Codex CLI selects its own default.
- `CODEX_AUDIT_MODEL_OPTIONS`: optional comma-separated list used to populate the frontend model selector.

The configured default is included in the options returned to the frontend even when it is not repeated in `CODEX_AUDIT_MODEL_OPTIONS`.

## Public Configuration API

Add a read-only endpoint that returns only non-sensitive Codex model configuration:

```json
{
  "default_model": "gpt-5.4",
  "model_options": ["gpt-5.4", "gpt-5.3-codex"]
}
```

The endpoint must not expose filesystem paths, credentials, runtime directories, or unrelated settings.

## Task Contract

`CodexAuditOptions` gains an optional `model` field. Both multipart upload endpoints accept an optional `codex_model` field and map it into this typed option.

Task metadata records:

- `requested_model`: the task override, or null.
- `effective_model`: task override, server default, or null when Codex CLI decides.
- `model_source`: `task_override`, `server_default`, or `cli_default`.

Existing clients that omit `codex_model` retain the current behavior.

## Validation

Model identifiers are stripped and validated before task creation:

- Maximum length: 128 characters.
- Allowed characters: ASCII letters, digits, `.`, `_`, `-`, `/`, and `:`.
- Whitespace and control characters are rejected.
- Values beginning with `-` are rejected.

Invalid API values return HTTP 422 with a user-facing validation message. Environment configuration is validated during settings construction so an invalid server default fails startup clearly.

## Runner Behavior

`CodexCliRunnerConfig` gains an optional immutable `model` field. Command construction adds:

```text
--model <effective_model>
```

before the prompt when a model is configured. The flag is omitted when the effective model is null.

Task overrides create a runner or audit-service copy with the selected model. Global runner configuration is never mutated, so concurrent tasks can use different models safely.

Raw frontend values are never appended to `extra_args`.

## Cache Isolation

The effective model is included in the review cache fingerprint. Reviews generated by one explicit model cannot be reused by another model or by the CLI-default configuration.

Changing only the frontend option list does not invalidate cached reviews. Changing the effective model does.

## Frontend Experience

Both advanced audit setting panels show a model selector with these choices:

1. Use server default.
2. Each model returned by the configuration endpoint.
3. Custom model.

Selecting Custom model reveals a text input. The form sends `codex_model` only when the user selects a preset override or enters a valid custom model. While configuration is loading or unavailable, the server-default option remains usable and custom input remains available.

The selected model is a runtime option only; the frontend does not make audit decisions.

## Error Handling

- Invalid model input is rejected before task submission.
- Failure to load model options does not block uploads; the UI keeps server-default and custom choices.
- A Codex CLI error caused by an unavailable model follows the existing controlled runner failure path and preserves the effective model in diagnostics.
- No automatic fallback to another model occurs because that would make audit provenance ambiguous.

## Verification

Backend tests cover:

- settings defaults and environment loading;
- model validation;
- runner command construction with and without `--model`;
- factory propagation of the server default;
- PTR and report-check multipart overrides;
- immutable per-task runner selection under concurrent task configuration;
- task metadata provenance;
- cache separation by effective model.

Frontend verification covers:

- configuration API parsing;
- preset and custom model form serialization for both task types;
- TypeScript compilation and Vite production build.

Final verification commands:

```bash
cd backend && python -m pytest tests/infrastructure/codex tests/application/test_codex_runtime_factory.py tests/api -v
cd backend && python -m pytest tests/ -v
cd frontend && npm run build
git diff --check
```

## Done Criteria

- A server default model can be set without code changes.
- PTR compare and report-check tasks can independently override the model.
- Concurrent tasks cannot affect one another's selected model.
- The executed command and task metadata expose the effective model without exposing secrets.
- Different effective models do not share Codex review cache entries.
- Omitting all new settings preserves the current Codex CLI behavior.
